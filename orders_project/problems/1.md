## Part 1: Write a macro (Jinja + macros) ✅

Create `macros/cents_to_dollars.sql` with a macro `cents_to_dollars(column_name)` that turns cents into dollars rounded to 2 decimals. Then change `models/staging/stg_orders.sql` to use it instead of `amt_cents / 100.0`.

**Macros built so far:**

| Macro | What it builds | Used in |
|---|---|---|
| `cents_to_dollars(col)` | `round(col / 100.0, 2)` | `stg_orders` |
| `convert_to_rundate(col)` | `strftime(cast(col as date), '%Y%m%d')`, so 2026-10-01 becomes 20261001 | `stg_orders` |
| `capitalize_status(col)` | `upper(col)` | not used. Keep status lowercase in staging |
| `count_by(col, [values])` | one `sum(case when ...)` count column per value | `playground_examples` |
| `safe_divide(top, bottom)` | `(top) / nullif(bottom, 0)` | `int_customer_metrics` |

**Lessons:**

- A macro is a **SQL builder**: it writes SQL text before anything runs. Check what it built in `target/compiled/`.
- Pass column names **in quotes**: `{{ cents_to_dollars('amt_cents') }}`. Without quotes, Jinja inserts an empty string and you get `round( / 100.0, 2)`.
- Comment out Jinja with `{# ... #}`, not `--`.

## Part 2: `fct_orders` mart (one row per order) ✅

`models/marts/fct_orders.sql` has these columns:

| column | meaning |
|---|---|
| order_id, customer_id, amount, status, order_date, order_rundate | from `stg_orders` |
| region, signup_date | from `dim_customers` |
| customer_order_number | the customer's 1st, 2nd, 3rd... order by date, with ties broken by order_id (**window function**) |
| is_first_order | true when customer_order_number = 1 |
| days_order_since_signup | days between signup_date and order_date (fixed per order) |
| days_customer_since_signup | days between signup_date and today (changes daily) |
| days_since_order | days between order_date and today (changes daily) |

**Lessons:**

- Staging already renamed and cleaned the columns, so marts use the **new** names (`order_id`, not `id`) and don't repeat the macros.
- `row_number() over (partition by customer_id order by order_date, order_id)` restarts at 1 for each customer.
- A comparison (`customer_order_number = 1`) is already true/false, so it doesn't need a `case when`.
- DuckDB and Snowflake let a later column reuse an alias from the same `select`. Postgres, SQL Server and BigQuery don't, so there you'd use a later CTE.
- If an "order" column has the same value on every row for a customer, it's really a **customer** column.

## Part 3: `region_scorecard` mart (one row per region) ⬜

| column | meaning |
|---|---|
| region | |
| total_customers | every customer in the region, including ones with no orders |
| buying_customers | customers with at least 1 completed order |
| completed_orders / cancelled_orders | counts |
| cancellation_rate | cancelled ÷ all orders, rounded to 2 decimals |
| total_revenue | completed orders only |
| avg_order_value | revenue ÷ completed orders |
| revenue_rank | 1 = highest revenue |

Watch out: EU has a customer with **zero orders** (108). Make sure they still count in `total_customers` and don't break the averages.

**Hints (from what you've already practiced):**

- `fct_orders` has no row for 108, so `total_customers` has to come from `dim_customers`. Start `from` customers and left join orders.
- Put a filter on the right-hand table in the **`on`**, not in `where`. A `where` there quietly drops customers with no orders.
- Use `safe_divide` for `cancellation_rate` and `avg_order_value`. Dividing by zero in DuckDB gives `NaN` or `Infinity` with no error, and in Snowflake it crashes.
- `count_by('status', ['completed', 'cancelled'])` can make the two count columns. (It names them `completed_count` and `cancelled_count`.)
- `int_customer_metrics` shows the same pattern **per customer**. The scorecard is the same idea **per region**.
- `revenue_rank` is another window function: `rank() over (order by ...)`.
